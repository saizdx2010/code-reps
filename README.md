# Code Reps

## A place to practice with intention

Code Reps starts with TypeScript and pairs coding exercises with plain-English lessons, progressive hints, and authored self-reviews. Local profiles keep each learner’s work separate, with no signup or paid tier.

| Learn | Practice | Reflect |
| --- | --- | --- |
| Searchable lessons, worked examples, and interactive knowledge checks | Coding reps, realistic debugging, multi-file projects, and optional timed interviews | Saved attempts, personal notes, recurring reviews, and evidence behind progress |

The workspace follows five steps:

1. **Understand** the task, examples, constraints, and vocabulary.
2. **Plan** your approach and identify edge cases.
3. **Solve** in the editor, run checks, and reveal hints when you need them.
4. **Explain** your decisions, tradeoffs, and complexity in plain English.
5. **Review** the result, reflect on difficulties, and return for fresh practice.

Practice writing scales with the task: one useful sentence for a small Foundations rep, a focused approach and boundary for other beginner reps, and deeper reasoning for larger problems. Plan and explanation are optional on sentence-scale and focused reps and required on reasoned reps; passing checks is always required, and difficulty and confidence are optional. The step bar marks each step Needed, Optional, or Done; the header keeps save status visible. Completion offers one next action, with a quiet option to stop for today. A completed attempt is the record of practice; there is no separate session to end. Existing drafts keep their format.

Plan and Explain offer optional English sentence starters above the writing field. Selecting one appends it to your draft and returns focus to the field; your writing saves normally. **Show Indonesian help**, beside Quick vocabulary in the brief, is off by default. It adds short Indonesian glosses where available and an English tips disclosure in Explain. English stays primary. This profile-scoped preference survives refresh in the current browser session and never enters learner backups.

After every check passes, a rep with an authored step trace also compares your code line by line with the trace's reference code, ignoring spacing and comments; a different approach can still be correct. After you complete a rep you have finished before, or a journey's independent or recall rep, **Then and now** under the Finish receipt puts your first earlier attempt beside today's (`src/compare-work.ts`): hints and confidence as saved, the plan and explanation, and, for the same rep, both versions of the code with a bar on lines found in only one (not for multi-file projects or Break it hunts, whose saved work is JSON). A related journey step shows evidence and writing only, since the tasks differ. A narrow panel switches between the two versions, today first. It compares you only with yourself and never scores which version is better. Both comparisons appear only after your own work is done.

Check results also show the editor's TypeScript errors for your files, labelled as separate from the checks: code can pass every check with a type error, and a clean type check does not prove the types a brief asks for.

> Passing checks establishes behavior. Plans and explanations use a self-review rubric; independent fluency and retention need evidence from unhinted work and later recall.

## What you can practice

- **TypeScript foundations:** playable reps and searchable knowledge lessons, with starting points for beginners and returning developers.
- **Guided tracks:** Foundations (TypeScript basics, reading and repairing code, how JavaScript runs) plus the tracks that build on it: Problem solving, Pattern Recognition, Frontend, SQL, Backend, and DevOps. The track picker suggests an order (SQL builds on Foundations, Backend on SQL, DevOps on Backend) as guidance only; nothing is locked. Interview rounds sit at the end of Problem solving, Frontend, and Backend and are untimed.
- **SQL and SQLite practice:** SQL reps take SQL text in a `query.sql` editor; four reps in SQL's Change data safely stage (a stock transfer with rollback, a per-customer JOIN report, a paid-only spending report whose checks also confirm no row changed, and an all-or-nothing restock) call SQLite from TypeScript, and Backend links to that stage instead of repeating it. Every check runs in a fresh in-memory SQLite database in the practice worker. The brief draws each table's columns and first rows from the same schema and seed the checks load, and a failed check shows the expected and received rows side by side with the first difference named. They work in browser development without the local service and never open the learner progress database. Checks establish SQLite's behavior on the authored data, not other SQL dialects or performance.
- **Backend services:** Backend opens by reading the parts of a request: splitting a target, decoding a query string, parsing a request line, reading headers in any letter case, and accepting a JSON body only when it is declared. It then routes requests: matching path patterns, choosing 404 or 405, cleaning and building paths, and picking the most specific route. Later it decides who may act (whether a session still counts, what a role allows, and which notes or loans a member may reach, answering 401, 403, or 404), keeps concurrent edits from being lost with version numbers, If-Match tags, and compare-and-set, runs background jobs with retries, dead letters, leases, and repeat-safe handlers, limits request rates with token buckets and sliding windows, and evolves its API with versions, compatibility checks, deprecation and sunset dates, webhook signatures, and webhook deliveries that arrive twice or out of order. Each handler is a function over request values that the checks call directly, not a live server.
- **DevOps policies:** DevOps reps are TypeScript functions that apply an authored policy to authored inputs: reading CI output (exit codes, the first real error in a noisy log, step conditions, compiler errors as annotations, and the step that failed a job) checking configuration (typed settings with defaults, a schema checked at startup, masked secrets, .env files, and drift between environments), working with versions (comparing and choosing semantic versions, sorting pre-releases, caret and tilde ranges, and lockfile changes), running pipelines (job order and loops, cache keys and fallbacks, the critical path, and skipping jobs a change cannot affect), building container images (which layers a change rebuilds, in one stage or several, the build context, image tags, and tag cleanup), deploying safely (rolling batches, blue/green switches, stable-hash percentage rollouts, paused canaries, and promote-or-roll-back decisions), keeping instances healthy (liveness versus readiness, check thresholds, restart backoff, check timing for slow starts, and draining before shutdown), and scheduling jobs (cron fields and the two-day-field rule, local times across clock changes, and the next run in UTC or a named time zone, with the time and zone always passed in), and watching a service (nearest-rank percentiles, error budgets and burn rates in whole numbers, latency targets per route, two-window burn alerts, and alerts that do not flap), and learning from incidents (a timeline across time offsets, durations, impact windows, recent changes, and a postmortem skeleton whose explanation the learner writes and reviews themselves). The checks call each function directly; they do not run a shell, Docker, a CI service, or a real network. The track ends with a hero project, shown as the trail's last step and opened in Library → Projects, containerizing a service and adding CI on the learner's own machine, recorded as a learner-reported self-review note that Code Reps never checks or counts.
- **React practice:** three reps render real React components in the sandboxed frame: one checks that subscriptions are released, one that list keys keep rows and ticks with their data, and one that stale request results are ignored.
- **Break it:** a quick bug hunt with a read-only suspect and its contract. You try one input at a time; each try runs the suspect and the contract on a fresh copy in the practice worker, inputs outside the contract are refused with the rule they break, and a catch is credited to the authored bug it exposes. Catch every bug, then name them in a sentence (self-reviewed). One hunt ships, Break pageCount, in Library → Testing with cases. See [Break it](./docs/BREAK_IT.md).
- **Real-world tasks:** checkout debugging, batch-pipeline predictions, an interactive browser directory, a ticket request handler, and behavior-preserving stock-report refactoring.
- **Skill journeys:** from arrays, words, and lookups through text building, validation, request ownership, timing policies, reliable requests, sorting, trees, linked lists, heaps, dynamic programming, graphs, grids, debugging, reading stack traces, reviewing suggested code, maintenance, DOM interactions, and composite widgets. Each pairs guided work with an independent problem and fresh recall after three days.
- **Algorithms & Data Structures:** collection operations before problem solving, stacks and queues, two pointers, windows, binary search, sorting, recursion, trees, binary search trees, graphs, linked lists, heaps, backtracking, and introductory dynamic programming. Pattern Recognition then asks you to choose the tool from the contract. See the [path guide](./docs/ALGORITHMS_DATA_STRUCTURES.md) for scope and expansion.
- **Pattern cards:** Lessons → Pattern cards (`#/patterns`, `src/pattern-cards.ts`) shows a short unlabeled contract and three tools. After you choose, it names the deciding signal and why the tempting alternative fits less well, then links a rep that applies the tool. Answers stay on the page and never count as evidence.
- **Practical concepts:** closures, reference equality, async ordering, subscriptions, dependency injection, cancellation, caching, retries, idempotency, and optimistic updates. Local async practice awaits deterministic injected fetchers (sequential records, parallel panel outcomes, and cancellable exports) without network or timer waits. See the [Practical Concepts guide](./docs/PRACTICAL_CONCEPTS.md) for the full scope and evidence limits.
- **Browser application journey:** a TypeScript state-modeling lesson and guided/independent/delayed-recall reps, plus three freely accessible external project levels using plain TypeScript and the DOM. Detailed requirements cover forms, persistence recovery, real promises, learner-written tests, and a runnable production build. External self-reviews are learner-reported and do not grant retained-skill status.
- **Personal practice:** two multi-file projects, weekly plans, notes, recurring reviews, self-assessment, and optional timed interview rounds.

Trail is home: your chosen track drawn as stages, with lessons placed before the reps that use them, and your next rep beside it. Below it, **Today** lists one new rep and up to two due reviews, each marked done once you complete it today, and a compact list keeps a saved draft. All tracks shows Foundations and the tracks that build on it, and holds the starting-point choice. Saved goals that name a retired path (typescript-browser, practical-concepts, real-world, ai-era, interviews) move to the track that absorbed it. Library holds exercises, lessons, projects, and interviews. Projects includes **Game of Life**, a toy that runs your own code (after the projects you build here, before the browser projects): three Library reps (`life-count-neighbours`, `life-next-cell`, `life-next-generation`) build its parts, and once all three are completed the board steps with your latest saved `nextGeneration` while a selected cell shows what your `countNeighbours` and `nextCell` say. It runs in the practice worker with the five-second limit, compares every generation with the rules, and pauses with the differing cells marked when they disagree. Play is started by you and stops on a settled board, after 200 generations, or when the tab is hidden; with reduced motion it offers Step ×10 instead. Nothing it does is saved or counted as evidence (`src/life-toy.ts`, `src/LifeToy.tsx`). Beside it, **Request console** (`#/request-console`) is the Backend track's playable reward: type a raw HTTP request, or pick an example, and it passes through your own latest saved solutions to eight Backend reps in the order a server reads a request (request line, target split, query decoding, headers, JSON body, path cleaning, route match, route choice) to a stand-in handler that shows what it would receive. A part is lit when its rep is completed with saved code. The request stops at the first part that is not lit (it is never filled in with a reference solution), that throws, or whose answer differs from its rep's written contract, and the console names that part with the call, your answer, and the contract's. It uses the Life toy's worker, five-second limit, and fresh worker after a timeout. The Backend trail's two request stages say how many parts are lit and how many reps remain until requests parse or reach a handler, and completing a part's rep for the first time says which part it lit, once per browser session. Fill in a path pattern and Pick the most specific route are not parts: one builds paths rather than reading them, and the other is a second router that would answer the same question differently. Lit means your code runs there, not mastery; nothing the console does is saved or counted (`src/toy-rewards.ts` lists each toy's parts, `src/request-console.ts`, `src/RequestConsole.tsx`, `src/ToyRewards.tsx`). Progress holds your skills and the Journal: completed attempts, notes, mistakes, and stuck points in one place.

**Quick warm-up** on Trail offers three short Beginner reps you finished at least a day ago, least recently practiced first and from different topics where possible (`src/warmup.ts`). Starting it opens the first rep from its starter, and the completion button leads through the rest. Unfinished drafts and recall reps that are not ready yet are never included, and a warm-up completion counts like any other attempt.

Progress shows your local profile, completion badges, your practice rhythm, and the evidence behind **Not started**, **Guided**, **Independent**, and **Retained**. Progress → Skill map (`#/skillmap`) draws each skill of a track as a node labelled Not started, Guided, Independent, Retained, or Review due, with a link to the next useful rep; the labels describe recorded practice, not mastery.

- **Badges** (`src/badges.ts`) are derived from completed attempts. Completion badges are a first-rep badge, one per track stage, and one per track. Evidence badges (`src/evidence-badges.ts`) reward learning rather than volume: first independent skill, first retained skill, five and ten skills kept, held for a month (a hint-free recall 30 or more days after independence), four steady weeks (3 or more practice days in each of 4 Monday-to-Sunday weeks in a row, reviews included), welcome back (practice after a break of 14 days or more), and stage, independently (every skill of one track stage at Independent, for stages of two or more skills, so one rep never earns it alongside first independent skill). Each badge is drawn from the logo (`src/BadgeArt.tsx`): a coding-desk tile with the code brackets and the three rep bars as the evidence ladder; square tiles are evidence and round tiles are completion, and the art follows Sage, Ocean, and Plum. Progress lists only earned badges, evidence first, quietly, with no upcoming list. An evidence badge names what earned it and opens that rep. Each distinct rep counts once at its earliest valid completion; hinted attempts count, and drafts and invalid or future dates do not. A completion badge's earned date is the latest first completion among its reps; an evidence badge's is the completion that earned it, shown as a calendar day in your timezone. Badges follow the current track definitions: a required rep added to an earned stage stops showing that badge as earned while its completed reps are kept. A newly earned badge shows a quiet notice once per browser session. Nothing is stored, so backups are unchanged. Badges do not establish mastery and are separate from independent and retained evidence.
- **Streaks** group completed attempts by calendar day in the current local timezone (`src/profile-progress.ts`). Any completed attempt makes a practice day, reviews included. A streak counts practice days and carries over a single missed day (a rest day) when no other rest day falls within seven days of it; two missed days in a row end it, and yesterday keeps it active until today ends. Beside it, Progress shows how many of the last seven days you practiced and draws them as one row (new practice, reviews only, a carried-over rest day, today); the 12-week calendar sits under **Last 12 weeks**. Imported completion history counts.
- **Learning moments** are worked out from completed attempts, so nothing is stored and backups are unchanged. When the attempt you just completed moves a skill to Independent or Retained, the completion panel says **Skill moved up** (Guided is never celebrated), and the skill map replays the change once, the next time it opens in that browser session. The panel may also show one note that compares the attempt only with your own earlier work (`src/personal-best.ts`): **Recall held** (a recall rep solved without hints at least 14 days after the skill's first hint-free rep), **Personal best** (no hints, after hints last time on that skill or rep), or **Fewer hints** (a repeat with fewer hints than last time, still at least one). First attempts, ties, worse attempts, and invalid or future dates show nothing. **Today** on Trail (`src/today-plan.ts`) is one new rep and up to two due reviews; it is recalculated from attempts completed today, starts again at local midnight, stays hidden when it would only repeat the next-practice panel, and never locks anything. With two or more open items, **Start set** runs them as one set: the due reviews first as a warm-up, then the new rep as the main rep. The workspace header shows **Set · 2 of 3**, each completion button leads to the next item, and the last one finishes the set back on Trail; when the main rep has an authored trace, it ends with a **cool-down** instead, opening that trace in predict mode. Opening a rep another way ends the set. The set is a session preference (never in backups), and each completion is an ordinary attempt.
- **Look back at the last seven days** sits at the top of the weekly plan (`#/plan`, `src/retro.ts`). It summarizes that week's attempts, unhinted work, most tagged mistake, and most common hardest part, and saves three short reflection answers as an ordinary Notebook note. It is not a skill measure.
- **The daily loop** (`src/daily-loop.ts`, `src/week-progress.ts`, `src/DayClosed.tsx`): Progress counts **Days this week**, Monday to Sunday, against a weekly target you choose (1 to 7 days; without a choice, your practice days from the weekly plan, or three). A missed day only matters if the week falls short, and a week still in progress never breaks your run of met weeks; the forgiving streak stays beside it. Before you finish anything on a day that starts with a new rep, Trail offers **Just one review** (or one short rep you finished before), since any completed attempt makes a practice day. **Done for today** in the completion panel, finishing a set, or **Finish for today** under a completed Today plan closes the day: Trail shows what today held (new reps, reviews, attempts without hints), this week against its target, and **Next time**, where you choose the rep to start with and may leave a note to your future self (280 characters). That rep then leads Trail as **You planned this**, with your note, until you complete it or choose something else, and the note shows again at the top of its brief. On a longer (reasoned) rep, once the plan is written and before checks pass, **Stop here and solve it next time** keeps the draft, sets that rep for next time, and closes the day. The weekly target and the chosen rep with its note are saved in learning data (`goal.weekly` and `nextUp`, both optional, so older backups load unchanged); the closed day is session UI state and ends at local midnight. Everything else is recalculated from completed attempts.
- **Coming back** (`src/come-back.ts`, `src/ComeBack.tsx`, `src/calendar-file.ts`, `src/reminders.ts`): after three or more days without a completed attempt, Trail opens with **Welcome back**: how long it has been, that nothing was lost, your reason for practicing (or a one-line prompt to write it), and **Ease back in** with a rep you finished before (not the one the next-practice panel suggests). **Skip to my plan** hides it for the rest of the day, and it disappears once you complete anything. When practice has slowed rather than stopped (four or more practice days in the two weeks before, and at most half as many, but at least one, in the last two), Trail and Progress say so with both counts, offer a lighter weekly target, and suggest a Break it hunt for a change of format; **Not now** hides it for the day. Journal → Plan → **Come back on time** holds your reason (160 characters), a practice time, **Add to my calendar** (an iCalendar file with a weekly event on each practice day, a ten-minute alert, and your reason), an optional reminder at that time on a practice day you have not practiced yet, and, in Chromium browsers that offer it, **Install Code Reps as an app** (`public/manifest.webmanifest`). Code Reps has no server that can message you: the reminder appears only while Code Reps is open in a tab or as an installed app, and the calendar file is what reminds you while it is closed. An installed app's icon shows the number of due reviews where the browser supports app badges. The reason, practice time, and reminder choice are saved in learning data (`reason`, `goal.time`, `goal.remind`, all optional, so older backups load unchanged); skipping the welcome or the note is session UI state.
- **Seeing progress** (`src/skill-growth.ts`, `src/month-look-back.ts`): the trail draws its line solid between completed nodes, and stronger where the later one was completed this month; Trail's heading counts reps completed this month. The next node says **You are here**, a started stage names what is left in it (for example, "2 reps, 1 recall and 1 lesson left"), and a recall rep that is waiting says when it opens ("Recall in 3 days"). Returning to Trail after finishing a rep pops that node's check in once (session UI state). On the skill map, an Independent skill counts down to its fresh recall, and a Retained skill whose next spaced review is due shows as **Fading** with the days since it was last held and a **Fresh review** link; its evidence is not removed. A Retained skill also offers **Then and now**: its first guided attempt beside the recall that retained it, with dates, hints, and the plan as written. **Your map over time** replays the map week by week from your first attempt, using only the evidence recorded by each week's end. Journal → Plan adds **Look back at the last 30 days**: skills that moved up, badges earned, tagged mistakes that came up less than in the 30 days before, and reps that went without hints after needing them, with one question saved as a Notebook note. In the Library, each rep row has an empty mark until it is completed and a filled check after, with its best evidence (fewest hints). Everything here is worked out from completed attempts; nothing new is stored.
- **Milestones** close what you finish, worked out from completed attempts (`src/stage-closeout.ts`, `src/track-finish.ts`, `src/starter-program.ts`); nothing new is stored except a reflection you choose to save. When the attempt you just completed finishes every rep in a stage of your goal track, the completion panel shows **Stage complete**: the stage's recap, its skills that are Independent or Retained (and how many are not yet), and a link to start the next stage. When it finishes a whole track it shows **Track complete** instead, linking to that track's finish page (`#/finished/<track id>`, reached from Skills, which lists every finished track): when you started and finished, days taken, your first and last reps side by side (evidence and writing, since the tasks differ), the skills reached, Notebook entries linked to the track's lessons or reps, and its badges. On Trail a finished stage folds to one row with its completion date, rep count, and recap, and its trail line is drawn solid. A lesson whose predictions are all checked closes with the first-check score and the first rep that uses it that you have not completed. **Your first 4 weeks** (`#/first-weeks`, linked from Skills) starts on the day of your first completed rep: each week takes the next reps of your goal track in trail order (recall reps come back as reviews instead), one per planned session of about 20 minutes and between two and six a week, with the lessons the trail places before them. Trail shows the week and this week's next target while it runs (the page lists every week), then its finish for one more week or until you save the reflection, which is an ordinary Notebook note. Completing a stage or a track counts finished reps, hints included; it does not prove mastery.
- **Mistake tags:** while reviewing a rep you can optionally tag mistakes from a fixed list (off-by-one, mutated input, missed empty case, wrong boundary condition, misread contract, type or null handling, other). Journal → Mistakes counts each tag, lists recent attempts, and compares the last 14 days with the 14 days before. Tags are self-reported, never block completion, and do not measure skill. They are stored as an optional `mistakes` array on each attempt (`src/mistakes.ts`), so older attempts and backups load unchanged.
- **Stuck points:** the optional “What was hardest?” answer now also offers “Something I had not learned yet” and “Combining the pieces”. Journal → Stuck points (`#/stuck`, `src/stuck.ts`) groups these answers, including saved drafts, by kind and by topic, suggests where to focus next with the rep's linked lesson or a nearer step, and gives one habit per kind. Journal → Mistakes now offers a habit and related lessons for each tag. Both are self-reported and never change skill evidence.

Practice sessions were retired from the interface. Existing `sessions:v1` records stay in storage and backups and still import, but they are no longer created or shown, and the old `#/sessions` bookmark opens the Journal.

Practical-concept traces check authored application policies; they do not establish live network or timer behavior. See the [learning tools and verification boundaries](./docs/FLUENCY_PLATFORM.md) for details.

## Get started

Requires **Node.js 24+** and **Yarn Classic 1.22.22**.

```sh
yarn install --frozen-lockfile
yarn dev          # development: saves work in the browser, no SQLite service needed
```

To run the local app with SQLite instead, run `yarn build` and then `yarn serve`. It binds to `127.0.0.1` and stores learner data in `~/.code-reps/progress.sqlite`. `yarn package` builds a portable local web bundle with its own Node runtime; see the [portable bundle guide](./docs/PORTABLE_BUNDLE.md).

Your work stays local: separate profiles keep each learner's work apart, **Progress → Download backup** exports a portable JSON backup, and the local server keeps daily SQLite snapshots. The [local setup guide](./docs/LOCAL_SETUP.md) covers installation, updates, backups, restores, and moving browser data to the local app.

## A focused workspace

| Control | Behavior |
| --- | --- |
| **Ctrl+Enter / Command+Enter** | Run checks from the workspace |
| **Stop checks** | Cancel the active run and keep your code |
| **Edit code** | Cancel an active run and clear obsolete feedback |
| **Tab** | Move focus out of the editor |
| **Tools → Vim keys** | Edit with Vim keys; `:make` runs checks, and Escape stays with Vim |

Monaco is the code editor, with a plain text fallback if it cannot load. Desktop layouts keep writing steps beside the editor; narrow screens show one pane at a time and keep save feedback visible. See the [UI guide](./docs/UI_GUIDE.md) for navigation, keyboard controls, and saved-state behavior.

Function reps execute authored code in a browser worker with a five-second timeout. Frontend reps use a sandboxed browser frame for previews and DOM checks, without an external service. These runners are for personal practice with code you write yourself, not secure isolation for arbitrary third-party exercises.

## Development

[Maintaining](./docs/MAINTAINING.md) lists every command, what each gate catches, and when to run it; [AGENTS.md](./AGENTS.md) is the same contract for coding agents. `just check` runs lint, build, tests, and content validation; `just check-all` adds the Chromium suite. Pull requests and pushes to main run these checks in CI.

Automated checks do not establish learning effectiveness, full disconnected-browser operation, cross-platform behavior, visual fidelity, or assistive-technology support. Those remain separate validation tasks.
