# Practice UI

This guide owns behavior: routes, navigation, keyboard controls, saved state, and session preferences. The [Code Reps design language](./DESIGN_SYSTEM.md) owns page structure, tokens, shared components, and motion.

## Voice and terms

Use US English: **practice** is both a noun and a verb. Write directly to the learner in short, friendly, plain English.

- **Track:** a curriculum, such as Foundations or Frontend. Code and saved data call it a path (`src/path.ts`, `goal.pathId`); learner-facing text says track.
- **Goal:** the track the learner chose as their current focus. A suggested default becomes the goal only when the learner chooses it, and browsing another track does not change it. Avoid “assigned course”.
- **Trail:** the visual path of stages on the Trail page.
- **Stage:** a group of related reps within a track.
- **Rep:** one coding exercise and its understand, plan, solve, explain, and review loop.
- **Lesson:** an explanation with examples and knowledge checks.
- **Due recall:** a scheduled chance to apply a previously practiced skill after a gap. It comes first in recommendations. Avoid “overdue assignment” or “mastery test”.

A completed stage replaces its description with a short recap of the work practiced. Descriptions and recaps load just after the trail; until they arrive, or if they cannot load, a stage shows its title, level, and progress. It does not establish independent fluency or retention. The editor header follows the active project file.

Progress and Journal share readable local dates and singular/plural labels. A zero Progress stat explains which practice unlocks it. Library topics are presentation labels shared by filtering and grouping; authored categories, rep IDs, and checked answers stay unchanged.

Briefs and lesson prose render paired backticks as inline code using the shared `InlineCode` component. All text stays escaped by React. Keep each rep's assessment limits in one “How this is checked” `InfoNote`: checks show tested behavior, while the learner reviews writing and variations. Task limits stay visible in the brief; only assessment sentences move into the disclosure. The checks drawer reports results.

## Navigation

- Main navigation has Trail, Library, and Progress. The second row contains only the pages in the selected area: Your trail and All tracks; Exercises, Lessons, and Projects; or Skills and Journal. The [information architecture](./DESIGN_SYSTEM.md#information-architecture) table lists each area's routes.
- Skills switches between Journeys and Skill map (`#/progress`, `#/skillmap`). Journal switches between Attempts (`#/history`), Notebook (`#/notebook`), Mistakes (`#/mistakes`), and Stuck points (`#/stuck`); each keeps its own bookmarkable route, and the retired `#/sessions` redirects to `#/history`. Timed interview practice (`#/interview`) is an optional link at the end of Projects. Projects has three sections, in-app first: Projects you can build here (milestones), the Game of Life toy, then Build on your own machine (one evidence note, one setup guide for the browser app and the service, and every external project in order). The toy shows a parts list until its three reps are completed, then a board whose 240 cells are one tab stop (arrow keys move, Enter switches a cell, I asks your code about it), with controls beside the board on a wide card and under it on a narrow one. Cells that differ from the rules carry stripes, an outline, and an accessible label. The weekly plan (`#/plan`) and self-assessment (`#/assessment`) are quiet links near the end of Skills. Their saved data is unchanged, and every old route still opens a page.
- Attempts keeps **Find an attempt** in view and folds Skill, Difficulty, and Date into a **Filters** disclosure (open by default on wide screens, closed on narrow ones, remembered for the session), like the Library. Each attempt is one header line (rep, date and hints, **Open rep**) above its **Review attempt** disclosure. Skill map keeps only the Journeys/Skill map switch in its header; its Track choice sits on its own row, and the legend gives each state a cell with its count and meaning.
- Each tool has a bookmarkable hash route, and each lesson has its own (`#/knowledge/<skill-id>`); choosing a lesson adds a history entry, so Back returns to the previous lesson. Existing `#/knowledge` (the last lesson of the session), `#/learn`, and exercise bookmarks remain valid, and an unknown lesson id opens the lessons page. Lessons opens full lessons; `#/learn` continues to open quick introductions, and `#/patterns` opens pattern cards.
- Exercise URLs use `#/practice/<rep-id>`. Pages and exercises support bookmarks, refresh, and browser Back/Forward.
- During practice, Navigate opens the main destinations in a compact menu. Escape closes it and restores focus to its summary. Profile management remains beside the profile name. Search opens the command palette; its keyboard shortcut is also available in the narrow workspace.
- Narrow screens keep save feedback visible on every page. Main navigation fits in four destinations; section navigation can scroll when needed. Search keeps a visible text label on browsing pages, and Ctrl/Command K remains available in practice.

## Find and resume work

- The header shows the active local profile and opens profile management. Switching is immediately available; creation/renaming and full-profile export/import open separately. Save feedback remains visible in the page navigation or workspace controls. Profile switching, creation, import, export, and deletion show an operation message while work is pending.
- Your trail (`#/home`) draws the goal track as stages of connected nodes, with the next practice beside it (above it on narrow screens). Each lesson appears once, immediately before the first rep that uses it; reps show done, next, in progress, or recall-later states, and project milestones end the trail. A track that ends with a project outside Code Reps, such as DevOps, shows it as a last node whose "Open project brief" opens Library → Projects with that project expanded, scrolled into view, and focused; it is never counted toward the track.
- The next-practice panel names the rep, its stage, and one reason line, with chips for level, role (Guided, Independent, or Recall), and a rough effort range; the goal is already the page title, so the panel does not repeat it. The panel's rep is always the trail's next node when it is on the drawn trail, so the two never disagree. On a first visit (no starting point, nothing started), the panel also offers **Skip the language basics** for returning coders; choosing it moves the panel and the trail to the first array rep, announces the new rep, and offers Undo for the rest of the visit. Below it, **Today** is a small card with a count, a segmented meter, and rows for one new rep and up to two due reviews, each labelled New, Due, or Done with its stage; a row is done once an attempt for it was completed today. When more reviews are due, See all due reviews opens Progress; when everything is done, the card says so and offers a quiet stop. With two or more open items, **Start set** runs them in one set (reviews first, then the new rep): a **Set · N of M** chip joins the workspace header's chips (no new toolbar), the completion button reads **Next in set: …**, then **Finish set**, or **Cool-down: call the steps of the trace** when the main rep has an authored trace, which opens Explain with the trace in predict mode. The Quick warm-up card sits under Today and loads with it. It is hidden when it would only repeat the panel's rep. An Also waiting list then offers at most one saved draft that is not the panel's rep, and Find saved drafts in the Library opens the Library when there are more. Opening a choice preserves the existing resume or fresh-review behavior. Trail links lead to progress and, after the first walkthrough, Replay walkthrough.
- All tracks (`#/paths`) holds the starting-point choice (New or Returning to coding) in a Starting as disclosure, then every track as a card: Foundations first, then the tracks that build on it, each with completed-rep counts, the goal marked, and what it builds on. Choosing a card selects the track and focuses its heading. On narrow screens the cards give way to one Choose track menu (the goal marked in it), which supports keyboard selection. The selected track's bar names it, says whether it is the goal (with Use this as my learning goal when it is not), and holds Start track or Continue track; the card above carries the description, so the bar does not repeat it. The track introduction starts folded. The selected track survives refresh in the session. Stages made only of Foundations reps are marked as covered by Foundations and link back to it.
- Exercises puts a sticky topic rail beside one open topic, so choosing a rep is a pick rather than a scroll. The rail starts with progress shelves that appear only when they hold reps (Start here, In progress, Review due, Completed), then the areas in learning order (the same names as the lesson groups), each listing its practice topics in learning order (`catalogAreas` in `src/catalog-labels.ts`) with N/M done. A new learner opens on Start here; otherwise the first non-empty shelf or topic opens, and the choice survives refresh in the profile's browser session (a topic saved under a retired label falls back the same way). The pane names the area and topic with a thin meter, lists the topic's reps easiest first, and ends with a Next topic link. Rows show the level, the format only when it is not a plain exercise, and a status chip only once there is a status. Level and Type filters sit in the pane header; while they are set, rail counts show matching reps. Search matches every word against the rep title, topic, format, and the titles of the lessons it practices, so concept words such as binary search find reps across every topic; when nothing matches it offers the lessons that mention the words. Empty results say why and offer Clear search or Clear filters. On narrow screens the rail becomes one Topic menu above the pane.
- Journal → Attempts filters completed attempts by rep or skill search, skill, difficulty, and local calendar date, and compares earlier and current code, plans, explanations, and hint counts. Written work remains self-reviewed.
- Returning to a screen restores its scroll position, open sections, and focus: to the control used last when it has an id (such as the trail node that opened a rep), otherwise to the page heading. Filters, the selected track, and the mobile workspace tab survive refresh in the same browser session.
- Editor cursor, selection, and scroll position are remembered per exercise. Learner drafts remain in the existing local store; session-only UI preferences do not enter backups.

## Goals and recommendations

Your trail draws the goal track. Browsing another track does not change the goal; choose **Use this as my learning goal** on All tracks to save that preference for the current profile. The action is offered only for a track that is not already the goal; once chosen, the confirmation line takes focus and is announced. Foundations is the starting suggestion.

Tracks identify guided, independent, and recall reps from the authored skill journeys, show recall availability and evidence, and connect the Frontend and Backend tracks to project integration milestones. Track completion includes hinted attempts and remains separate from independence and retention. Early recall can be opened freely, but existing timing and hint rules still govern retention evidence.

Due recall remains first in recommendations. Drafts within the chosen track take priority over new reps in that track; other drafts remain visible for explicit resume. Existing difficult-review scheduling remains available. Completed attempts show the reason for the recommended next action.

## Browse learning content

- Lessons opens full lessons. Its index groups lessons by topic under one search (**Find a lesson**), with Quick lessons and Pattern cards on a quiet line beneath it; bookmarked lessons gather in a Bookmarked group above the topics, and lessons whose predictions are all checked show a check. Search needs every word, lists title matches first, and opens matching groups; an empty result offers Clear search. The search survives refresh in the same profile and browser session. On narrow screens, Browse lessons starts collapsed and selecting a lesson closes the index and focuses the reader. Selecting a lesson scrolls to its content and moves keyboard focus there.
- Lessons have focused Read, Predict, Practice, and Review views. Tabs show progress (predictions checked, reps done), and each view ends with a button to the next. Read uses the full text colour; **Reason it through** has a session-only field for the learner's prediction, and the discussion opens beside it for comparison. Practice lists the lesson's reps as rows with level and status; a rep opened there shows a back link to the lesson in the workspace header. Review opens the evidence and self-assessment disclosure. Moving between views keeps predictions and written evidence mounted; the selected view survives refresh per lesson and profile.
- A prediction's first check is its evidence. After checking, the answer and a wrong choice are marked in place and the feedback names both; changing the choice hides the verdict until the next check. Later checks are labelled practice and never overwrite the first, so evidence reads N of M predictions correct on the first check. Predictions remain distinct from independent coding evidence.
- Quick lessons inside the lesson index opens short introductions. The existing `#/learn` bookmark still works.
- Self-assessment groups skills by knowledge topic while retaining each skill's supporting evidence and the optional assessment flow. Project summaries disclose milestones and final self-review.

## First rep walkthrough

While Declare a value is the next rep, Trail offers **Show me how a rep works**, a walkthrough around that real rep. After starting it, **Replay walkthrough** stays among the trail links, keeping the daily choices prominent. Inline help follows Understand, Plan, Solve, Explain, and Finish; normal step navigation remains available. The guide introduces saved writing, behavioral checks, optional recorded hints, and the existing completion checklist without inserting a solution, completing an attempt, or granting mastery. Skip or Finish dismisses the help; replay opens the existing draft without resetting it.

Walkthrough visibility is a profile-scoped session UI preference through `useSessionPreference`, survives refresh in that browser session, and stays out of learner backups. The guide appears only on its rep and resumes on return until dismissed; Back/Forward and reload use the existing routes and draft owners. The editor remains mounted while changing steps. Focused Chromium flows cover skip/replay (including completed attempts), dismissal focus, real checks and completion, profile separation, guide-load failure, and short/narrow-screen draft preservation. Desktop and phone Solve layouts were also inspected in Chromium on macOS; this does not establish all-screen visual fidelity, browser zoom, other platforms, disconnected operation, or assistive-technology support.

## Arrange the workspace

The [practice workspace](./DESIGN_SYSTEM.md#practice-workspace) section describes the layout. Its behavior:

- One compact header row carries the back link, previous and next with the rep's position, exercise title, level, the rep's trail role (Guided, Independent, or Recall), status chip, category with a rough effort range, save status, Glossary, and Tools. Tools contains focus mode, Vim keys, Reset rep, and related concepts. Escape closes Tools and returns focus to its summary.
- The back link names the page the rep was opened from (Your trail, All tracks, Library, Projects, Skills, or Journal, or the lesson with its book mark) and returns there with its scroll position; a rep opened from search, a bookmark, or another rep's link keeps the origin it had, and without one the link leads to the Library. The origin is a session preference, never part of a backup.
- Previous and next step through the same list the rep came from: the lesson's practice reps, the track's reps in trail order (the goal track, or the first track that holds the rep), or the rep's Library topic, easiest first. The position between them (such as 3/12) opens a switcher listing that list with each rep's status, scrolled to the current rep; choosing one opens it, and Escape closes it and returns focus. Stepping keeps the original back link. The stepper loads just after the header; on phones it shares the first row with the back link, Glossary, and Tools, and the switcher spans the header.
- Desktop practice uses a fixed split workspace: the task pane and editor scroll independently, while the step bar, save status, and Run checks stay visible. A new learner starts with a 40/60 reading/code split. Drag the divider between brief and editor, or focus it and use Left/Right to resize, Home/End for the limits, or double-click to restore the default split. The split preference is saved locally.
- Focus mode expands the coding workspace. Use Exit focus in Tools or press Escape to return; selecting a writing or understanding step also exits focus mode.
- Vim keys (Tools, or Search › Settings) turn on a Vim keymap in the code editor through `monaco-vim`, which loads only when chosen. A status row under the editor shows the mode, pending keys, and the `:` and `/` prompts; mode changes are announced politely. With Vim keys on, Escape in the editor belongs to Vim and does not leave focus mode. `:make` runs the checks and `:w` says the draft already saves as you type. Ctrl/⌘ Enter still runs the checks in either mode, and the browser keeps Ctrl-W. Yanks use Vim's own registers, not the system clipboard, and there is no `.vimrc`. The setting belongs to the browser (`localStorage` key `code-reps-device:vim`, outside the `code-reps:` namespace that profiles, sync, and backups own). If the keymap cannot load, the editor keeps its usual keys and says so; the plain text fallback editor has no Vim keys.
- The brief opens with a collapsed **About this rep** note (`src/RepGuidance.tsx`, derived in `src/rep-guidance.ts`): a rough first-attempt effort range by authored level, up to two lessons the rep practices under **Before you start**, the foundations those build on behind one toggle, and unfinished earlier reps in the same stage. The note folds away when the learner leaves Understand. When a rep is two or more levels above anything completed, a readiness checkpoint offers an optional lesson and the nearest easier earlier rep as a bridge. Estimates are guidance only, never change with learner speed, and nothing is locked.
- Understand, Plan, Solve, Explain, and Finish navigate the practice loop without enforcing a sequence. The brief is available during Understand and Solve; Plan, Explain, and Finish each show their own writing or finishing view. Finished steps show a check in the step bar, and optional steps a dashed ring; Finish reads To do, Ready, or Done, never Optional, because it is where the rep is completed (its id stays `review` in saved session state). The editor remains mounted beside the selected step. Step status descriptions report written work and behavioral checks, not an assessment of understanding or writing quality. The selected step is a session preference.
- The toolbar below the editor keeps Run/Stop and result counts within reach. Checks open as a drawer inside the coding desk, directly above that toolbar: it starts as a slim bar, expands on running or selecting Results, scrolls internally while the editor shrinks, and can be collapsed without discarding feedback. Passing checks puts **Explain your solution** in the summary line until an explanation exists. Editing code clears the verdict at once (stale results never count toward Solve or completion) but keeps the last run in the drawer as an **Out of date** reference: the open failed case stays legible with its input, expected value, and last actual value, the header reads Last run: N of M passed, and the toolbar invites a fresh run. Failed checks link to at most one lesson the rep practices, never a guess from check names.
- On narrow screens, Solve shows the coding pane with checks under the editor. On phones (≤600px) the run toolbar is fixed to the bottom edge and checks become a bottom sheet: closed, only its toggle peeks above the toolbar; a run raises the results over the editor (at most 72% of the screen), and the toggle or Escape lowers it. With results open, the count appears once, in the summary line; the other steps show only their selected task or writing view. Both panes remain mounted, preserving drafts, file selection, cursor, selection, preview interactions, and editor scroll position.
- The editor begins loading when an exercise row is hovered or focused. Editor recovery remains available if loading fails.
- A **Break it** rep (`format: 'break'`, [Break it](./BREAK_IT.md)) has no editor: Solve shows the read-only suspect, one field per parameter with **Try it** (Enter also tries), and a log of tries, newest first, in place of the editor, checks drawer, and run bar. An input outside the contract is refused with the rule it breaks and focuses its field; a repeated input points at the earlier try; while a try runs, Try it becomes Stop, and stopping adds nothing. A catch strikes the suspect's answer and adds a **Caught one** chip; the catch card counts distinct authored bugs and holds the one-sentence field, which is the attempt's explanation. The tries are the draft's code, so they survive reload, navigation, and profile switches and enter backups like any draft; opening a hunt reruns its saved tries in a fresh worker before Solve counts as done.

Plan and Explain offer optional English sentence starters above the writing field. Selecting one appends it to your draft and returns focus to the field; your writing saves normally. **Show Indonesian help**, beside Quick vocabulary in the brief, is off by default. It adds short Indonesian glosses where available and an English tips disclosure in Explain. English stays primary. This profile-scoped preference survives refresh in the current browser session and never enters learner backups.

## Checks and completion

- The first failed check expands to show the failing input, expected and actual values where available (differing lines marked), one sentence naming how the values differ (`src/value-diff.ts`: an extra or missing item by index, how far off a number is, the first differing character, missing or unexpected keys, or a different kind of value; it describes the values and never suggests a fix), and actionable feedback. A failed check's details load with the first failure, so startup and passing runs do not pay for them. After a run, the summary appears at once and the rows land in reading order, failed rows first, 40 ms apart (rows from an out-of-date run stay still). **Predict, then run** (`src/check-calls.ts`) is optional: before the first run the open drawer asks one question, whether every check will pass, because check names are not shown until a run reveals them; once a run is out of date, each check row offers a Pass or Fail call for the next run. The next run judges the calls once (one sentence, a **Called it** or **Surprise** chip per called row, surprises sorted first and opened first), then clears them. Calls live in the drawer for the session and are never saved, shown on Progress, or counted as evidence. The first all-green run of a rep with no completed attempt adds a **First all-green run this session** chip to the summary; later runs, reps completed before, and reps that already showed it this browser session stay quiet (runs are not stored, so the claim stops at the session). Nothing about these is stored. Selecting another failed check opens that case and closes the previous one. Passed checks remain visible as rows with right-aligned outcomes in the checks drawer. A failed SQL check shows its starting data and the expected and received rows as two tables, then one sentence naming the first difference; when SQLite cannot run the query text at all, the drawer shows SQLite's message with the line and a caret instead of the check rows. While a SQL rep's engine loads, the drawer says Loading SQLite.
- Finish starts with **Ready to finish?**: the requirements as chips (plan, passed checks, and explanation where required, plus optional reflection), then the optional reflection (difficulty, confidence, and mistake tags as chips that wrap), then Complete rep last. Reflection comes before completing so the saved record carries it; nothing on the Finish pane edits a completed attempt. When something is missing, one line names it with a Go to link for that step.
- Finish links to the first missing plan, checks, or explanation. Completion always requires passed checks. Plan and explanation are required on reasoned reps and optional on sentence-scale and focused reps; difficulty and confidence are always optional, and empty sections are hidden in the Journal. Written work remains self-reviewed, and none of these fields establishes independence or retention (those come from hints, checks, and recall timing). Finish also offers optional, self-reported mistake tags from a fixed list as toggle chips; they never block completion.
- Completion replaces the Finish pane with the completion panel, scrolls it into view, and moves focus to it. The panel names the rep once, then says what the attempt counts as from saved history when the rep belongs to a journey: hint use as practice, a hint-free independent rep after its guided rep as independent (with the date recall opens), a hint-free recall after the break as retained. A receipt lists the attempt's facts (checks passed, hints used, plan and explanation written or skipped) and the recorded reflection. It then offers the next rep and Done for today; its footer notes that the attempt is in the Journal and offers Start a fresh attempt.
- On Independent and Recall reps, the first hint asks once, inline, that a hinted attempt counts as guided practice; focus starts on Keep trying and returns to the hint control. Guided and other reps reveal hints in one click, and every hint control notes that hints are recorded.
- After checks pass, Explain leads its post-solve material with **See it run**, the authored reference trace, open without another click. It never appears before checks pass, so it cannot hint at the approach. The model answer stays behind **Compare with a model answer**.

## Progress

- Skills (`#/progress`, titled Skills with the profile name in the eyebrow) leads with an **Up next** strip: the first due review with its reason, or the trail's next rep, plus any further due reviews in place. Below it, two cards: a practice-rhythm card (three stats: the forgiving practice-day streak, how many of the last seven days were practiced, and completed reps, whose note gives the next recall date when no review is due; then the last seven days in one row: a check for new practice, arrows for reviews only, dashed for a carried-over rest day, and today) with the 12-week calendar under a **Last 12 weeks** disclosure (filled: a hint-free rep that day; outlined: practiced with hints), and a skill-ladder card that places every journey skill once on its highest rung. Ready reviews are counted once, in the Up next strip. Before any rep is finished, one welcome note (**Your skills show up here after your first rep.**) replaces the counts, ladder, journeys, and badges, so a new profile never sees a wall of zeros. Zero-state hints depend on context, so a lapsed streak says to practice today rather than to finish a first rep. Earned badges sit in two labelled groups, Evidence then Completion, side by side when they fit.
- One evidence ladder is used on Skills, the skill map, the self-assessment, and the trail: Not started, Guided, Independent, Retained, with Review due as an overlay (`stageLabels` in `src/learning.ts`). Journeys are grouped In progress (open, due recall first, then most recent), Retained, and Not started (always collapsed; before any journey has started, an empty state above it says so); each row shows a connected three-rung ladder. Expanding a journey exposes its supporting attempts. None of this is an overall coding score. Your trail owns the next-practice recommendation.
- Practice backup controls in Progress open on demand (**Back up or restore practice**). Choosing a file never writes anything: a valid backup opens a **Check before merging** preview naming the file, the profile it merges into, how many of its completed attempts and notes are new, and how many empty drafts it fills; existing drafts and goals stay. **Merge into {profile}** writes and reloads, and Progress then shows a one-time receipt (kept in session storage, so it never enters a backup). An invalid file shows an alert and says nothing was changed. This merge differs from a full profile file in Profiles. Timed interview setup selects a focus and duration before starting a round.
- Skill map (`#/skillmap`, `src/SkillMapPage.tsx`) reuses the trail stage and node styling to draw each skill of a chosen track (the goal by default). `src/skill-map.ts` derives one state per skill from the existing journey evidence only: Retained (fresh recall solved without hints after the break), Review due (independent work recorded and the recall break has passed), Independent (a hint-free related rep after the guided rep), Guided (guided rep completed, with or without hints), otherwise Not started. Every node pairs a `StatusChip` with text and a distinct marker, and links to the guided, independent, or recall rep as appropriate; waiting and retained skills show a date or note instead. A legend and an `InfoNote` state that the labels describe recorded practice evidence, not mastery.

## Profiles

- Manage profiles opens **Local profiles**: switch profile, then three disclosures. **New profile** and **Rename {profile}** each have their own name field, so a name typed for one never applies to the other. **Full profile file** exports everything in the current profile or imports a file as a new, separate profile; it explains how it differs from merging a practice backup on Progress. With one profile, the delete control is replaced by the reason it cannot be deleted.

## Retired practice sessions

The separate practice session (Record a session, Reflect and end session, Unfinished sessions, Practice history) is no longer in the interface; a completed attempt is the record of practice. Existing `sessions:v1` data is kept: it is still validated and imported from backups and profile exports, and it never contributed to streaks, completion, independence, retention, or recall scheduling. The `#/sessions` route redirects to the Journal. [Maintaining](./MAINTAINING.md#retired-practice-session-records) describes the contract.

## Reference and preview

- Glossary opens a searchable drawer without leaving the exercise.
- Frontend previews support fit-to-panel, phone (375px), tablet (768px), and desktop (1280px) widths. Larger previews scroll horizontally when needed, within their own bounded area.
- Expanded preview uses a modal with the same running frame and size controls. Expanding or closing the modal preserves preview interactions; Update preview deliberately restarts it with the latest code; changing the request scenario also refreshes an existing preview.

## Keyboard

- Ctrl/Command K (or the Search button) opens **Search** with focus in its field, so typing searches at once; the glossary drawer also opens in its field. Results are grouped and named like the navigation: Continue (the trail's next action), This rep (run checks, editor focus, focus mode, brief, results, explanation; in the workspace only), Lessons, Exercises, Pages (such as Library › Lessons), and Settings (Appearance, Dark mode, Vim keys, Manage profiles, Download practice backup). An empty query shows Continue, This rep, Pages, and Settings rather than the whole catalog. Every query word must match the start of a word in a title, topic, lesson summary, or the lessons a rep practices, so "closure" finds the closures lesson and its reps; titles that start with the query rank first, and Lessons and Exercises show at most 4 and 8 results. Up/Down moves; Enter opens; Escape closes. `src/command-search.ts` owns the entries and matching.
- Ctrl/Command Enter runs checks in the workspace, including the editor.
- Practice steps use direct buttons with hover feedback and no tooltips. The full profile name appears on hover or focus; Escape dismisses that tooltip while keeping focus on its trigger.
- Dropdowns keep focus on their trigger. Arrow keys explore options, Home/End reach the first/last option, and typing searches option labels. Enter or Tab applies the highlighted option; Escape closes without changing it. Menus use the browser's popover top layer to avoid clipping inside panes and dialogs; this requires a browser supporting the Popover API.
- The calendar opens with focus on the selected date or today. Arrow keys move by day/week, Home/End reach the week's boundaries, and Page Up/Down changes month while preserving the day where possible. Shift with Page Up/Down changes year. Enter selects a date; Escape cancels and returns focus. Clear date removes the filter. Values remain local `YYYY-MM-DD` dates.
- File selection opens the operating system's file chooser.
- Focus outlines, native modal focus containment, and reserved feedback space support continuity. Reduced-motion preferences disable UI animation and smooth scrolling; see [Motion](./DESIGN_SYSTEM.md#motion) for what moves and its fallbacks.

## Ownership

Your trail, All tracks, and the exercise library render in `HomePage.tsx`, `PathsPage.tsx`, and `PracticeCatalog.tsx`. `App.tsx` retains their session preferences, navigation, draft persistence, practice recommendations, and runner lifecycle. Presentation extraction does not introduce a second source of learner state.

See [the accessibility walkthrough](./ACCESSIBILITY_REVIEW.md) for manual screen-reader, zoom, contrast, and learner checks that automated keyboard and narrow-layout tests cannot establish. See [performance budgets](./PERFORMANCE.md) for local editor-loading measurements and verification limits.
