# Local loading and bundle budgets

`yarn build` produces Vite's manifest and runs `scripts/check-bundle.mjs`. It reports raw and gzip JavaScript bytes in `dist/bundle-size.json` and fails when either budget is exceeded. Gzip is a size comparison, not a claim that the local server compresses responses. CSS, fonts, and HTML are not included in these JavaScript budgets.

| Group | Raw byte budget | Gzip byte budget |
| --- | ---: | ---: |
| Initial route JavaScript and static dependencies | 530,000 | 157,500 |
| Additional editor JavaScript, including its dynamic language modules | 4,200,000 | 1,050,000 |
| Additional frontend preview/check JavaScript | 3,900,000 | 1,050,000 |
| Editor, TypeScript, and practice worker JavaScript | 12,150,000 | 3,100,000 |

The script deduplicates shared chunks within each group, excludes initial-route dependencies from the additional groups, and requires all three local workers. Worker totals also include their shared and dynamically imported JavaScript chunks. It also rejects unused CSS, HTML, and JSON language workers. Editor and frontend groups describe separate features; their totals are not a sum of every possible network request.

Monaco remains lazy, with existing hover/focus preloading and a plain text recovery editor. `src/monaco.ts` retains editor contributions from the locked Monaco release but registers only TypeScript, JavaScript, and SQL language support; the SQL registration is a few hundred bytes and its keyword tokenizer loads only when a SQL model opens. The previous general import also bundled CSS, HTML, and JSON workers plus many unused language modules. Removing those workers alone avoids approximately 2.26 MB of raw build output. This does not imply a corresponding startup-speed improvement: unused workers were not necessarily loaded on the first route.

The learning-tools presentation in `LearningHub.tsx` also loads on demand. Home, the library, and workspace keep their existing owners. A pending learning route displays local practice-sheet placeholders; load failure offers reload, and replacing a focused loading view restores the real page heading. This split keeps the shared design and motion within the existing initial JavaScript budget without changing learner persistence.

Secondary route pages (`PathsPage`, `ProgressPage`, `SkillMapPage`, `MistakesPage`) and the `TraceViewer` in the review panel also load on demand through `lazyRoute` in `src/lazy-route.tsx`. Each shows a `RouteLoading` placeholder with its page heading while the chunk loads, and a failed load offers a reload without touching saved work. Home, the library, and the workspace stay in the initial chunk. `tests/catalog-index.test.mjs` fails if `App.tsx` imports these modules statically again. This reclaimed headroom for new reps: initial JavaScript went from 530,571 raw / 152,008 gzip bytes (over the then-current 530,000 / 153,000 budgets) to 499,742 raw / 143,606 gzip bytes, about 30 KB raw and 9 KB gzip under budget, with no budget changed. The remaining startup weight is mostly React DOM plus `src/catalog-index.ts`. Starter code has since left that catalog: it keeps only `starterHash` (`src/starter-hash.ts`, shared with `practice.ts` so "unchanged starter" stays a synchronous check), and the starter text loads with the rep's other content through `useRepContent`. Initial JavaScript went from 522,951 raw / 148,044 gzip bytes to 462,087 raw / 138,291 gzip bytes with no budget changed. An attempt with no saved draft has no code until that content arrives, so the editor shows a short loading state; it is never saved in that state, and a saved draft is shown immediately and never replaced by the starter.

The SQL track added startup data (its path stages, journeys, lessons, and catalog rows) while staying inside the 153,000 gzip budget: track introductions moved to `src/path-introductions.ts`, which only All tracks loads; the generated catalog stores rep entries as compact rows instead of repeated object keys; and the unused first-mistake text left the lesson index. Together these saved about 4.3 KB gzip before new content was counted. The SQL track's sixth stage still crossed 153,000 (153,207 gzip bytes), because a track's stages, journeys, lesson summaries, and rep entries must be synchronous for Home's Trail, the practice plan, and fluency validation. The gzip budget was raised to 157,500 to hold the rest of the planned SQL track (five more stages), and the worker's raw budget from 11,700,000 to 12,000,000 because the worker bundles every rep's checks and seed data. Each later track should check this headroom again before raising it.

Before the Backend track's second new stage, the startup catalog reclaimed about 4.4 KB gzip with no budget changed: each rep's difficulty level is now copied into its catalog row by `yarn content:index`, so `src/rep-levels.ts` (one entry per rep ID) no longer ships at startup and `repLevel` reads the catalog, and the starter fingerprint shrank from 64 to 32 bits, which still tells a draft from its starter (a test checks that no two distinct starters share one). Initial JavaScript went from 156,412 to 152,018 gzip bytes.

After the Backend track's routing stage (152,507 gzip bytes), the track descriptions and every stage's description and recap moved from `src/path.ts` to `src/path-text.ts`. The trail needs only stage titles and rep lists to draw itself, so Home loads the text beside the trail (`usePathText`) and All tracks imports it with its own lazy chunk; a stage shows its title, level, and progress until the text arrives, or if it cannot load. Initial JavaScript went from 152,507 to 147,770 gzip bytes with no budget changed, and later stages add their text to that 5.9 KB gzip chunk instead of to startup.

The DevOps track crossed the worker's raw budget at its eighth stage: 12,007,529 raw bytes against 12,000,000, while its gzip size, 2,878,355 bytes, stayed well under 3,100,000. The practice worker imports every rep through `src/rep.ts`, so each rep's whole text (brief, notes, hints, and checks) ships in it; the seven DevOps stages before it added 19,543 to 27,046 raw bytes each, the eighth added 22,459, and Backend's API-evolution stage added 29,770. The raw budget was raised once, to 12,150,000, which holds the two remaining DevOps stages with about 90 KB to spare; no other budget changed. Sending only the open rep's checks to the worker would remove most rep text from it, but changes the run request between the page and the worker, so it is left for a separate change with its own browser coverage.

The practice worker now loads one rep at a time. The run request names the rep's content chunk (`source`), and `src/runner.worker.ts` imports that chunk through `src/rep-chunks.ts` and runs it with `src/run-rep.ts`; `src/runner.ts` keeps the by-ID API for tests and scripts. The worker's entry went from 4,807,175 to about 3,540,000 raw bytes, and a run loads the entry plus one rep source instead of every rep. The worker budget still counts every lazy chunk, so its total (12,087,156 raw bytes) barely moved; what each run loads did. `src/practice-worker.ts` also keeps one spare worker that has loaded its script, the open rep's chunk, and (for SQL reps) the SQLite engine before Run is pressed. Each run still uses a fresh worker once and terminates it, so learner code cannot leak state between runs, and the next spare starts after a run ends.

Frontend reps no longer load the TypeScript compiler on the page. `src/frontend-frame-html.ts` builds the frame from already compiled code, and the page compiles in a long-lived practice worker that only transforms text and never runs learner code. `src/frontend-frame.ts` still compiles synchronously for tests. The frontend preview/check group went from 3,710,891 raw / 1,042,390 gzip bytes to 239,639 raw / 74,600 gzip bytes, and the first preview no longer blocks the page while the compiler loads. A compiler that fails to load or does not answer within 30 seconds reports a recoverable error and keeps the draft.

The SQLite browser suite attaches Home and editor readiness durations alongside the bundle report. It uses the built app and a fresh browser context on the local machine, without CPU/network throttling. Measurements include Playwright observation overhead and are not representative of every learner's hardware. Shared CI timing has no hard speed threshold; byte budgets provide the reproducible regression gate.

When a dependency or content change exceeds a budget, inspect the manifest and measured flow before changing the limit. Keep TypeScript assistance, editor keyboard operation, recovery, and local worker behavior covered by the browser suite. Large editor/compiler chunks still trigger Vite's warning; it remains visible. The budgets establish current size limits, not a claim that loading performance is fully optimized.

Reps with a `sql` block lazy-load sql.js in the practice worker. The production build bundles its WASM locally (659,806 raw bytes, 322,711 gzip bytes in sql.js 1.13.0); this binary is additional to the JavaScript budgets above. It is fetched only when such a rep runs, never from a CDN. The SQL brief's tables and the drawer's row comparison load as their own small chunks with the first SQL rep. The worker JavaScript budget includes the lazy SQLite loader. See [ADR 0002](./adr/0002-in-memory-sqlite-practice.md). Asset bundling does not establish disconnected-browser operation.
